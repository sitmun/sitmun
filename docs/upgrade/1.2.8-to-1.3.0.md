# Upgrade 1.2.8 to 1.3.0

Back up the database before upgrading. Then count log rows that point at a missing application, cartography, task, territory, or user:

```sql
SELECT COUNT(*) FROM stm_log child
WHERE (child.log_appid IS NOT NULL AND NOT EXISTS (SELECT 1 FROM stm_app parent WHERE parent.app_id = child.log_appid))
   OR (child.log_giid IS NOT NULL AND NOT EXISTS (SELECT 1 FROM stm_geoinfo parent WHERE parent.geo_id = child.log_giid))
   OR (child.log_taskid IS NOT NULL AND NOT EXISTS (SELECT 1 FROM stm_task parent WHERE parent.tas_id = child.log_taskid))
   OR (child.log_terid IS NOT NULL AND NOT EXISTS (SELECT 1 FROM stm_territory parent WHERE parent.ter_id = child.log_terid))
   OR (child.log_userid IS NOT NULL AND NOT EXISTS (SELECT 1 FROM stm_user parent WHERE parent.use_id = child.log_userid));
```

A count other than zero stops the upgrade with `STM_LOG orphan count` and that count. The upgrade does not delete the row. Delete or repair it, then run the upgrade again.

Set `SITMUN_UPGRADE_DEFAULT_LANGUAGE` the same way as the [1.2.9 upgrade](1.2.9-to-1.3.0.md).

The catch-up is [01-catch-up.postgresql.sql](../../sitmun-backend/src/main/resources/db/changelog/upgrade/1.2.8-to-1.2.9/01-catch-up.postgresql.sql) and [01-catch-up.oracle.sql](../../sitmun-backend/src/main/resources/db/changelog/upgrade/1.2.8-to-1.2.9/01-catch-up.oracle.sql). Each 1.2.9 step is its own changeset. A step runs when the legacy schema is present and that step's 1.2.9 changelog row is absent. Adding a column, a key, or a row is also skipped when that object is already there, so a rerun after a partial Oracle failure does not repeat finished work. It does not put back a task a partner deleted after 1.2.9 had recorded the step.

The catch-up adds `TNO_DEFAULT`, `ATR_ID`, and `ATR_ORDER`, moves the application-tree primary key to `STM_ATR_PK`, and adds `STM_ATR_UK`. On Oracle the old key name is read from `user_constraints`, because 1.2.8 stored it as a `SYS_C` name. It widens a column only when the column is shorter than the 1.2.9 length, and it adds each missing `STM_LOG` foreign key. It inserts task types 17 and 18 when those ids are absent. It does not restate changeset 22c. The 1.2.9 hop inserts the `documentExport` code values. It inserts the four PDF tasks and the two default templates when no task of that type has that name, one statement per row, using the next free task id. It restates the three authentication-mode updates. It sets `USE_USER` to `admin` on user 1 when that name is null.

Oracle 11 and Oracle 21 cannot run 1.2.9 changeset 22c. A 1.2.9 database on those engines uses [26_map_image_task_type_pre23.yaml](../../tools/tests/26_map_image_task_type_pre23.yaml) in that slot. The version check treats those rows as that slot. A 1.2.8 database never ran 22c, so the catch-up inserts the task types directly.

Oracle 19c was not tested. Oracle 21 is the stand-in. After the catch-up, the upgrade continues with the [1.2.9 guide](1.2.9-to-1.3.0.md).
