# Upgrade 1.2.9 to 1.3.0

Set `SITMUN_UPGRADE_DEFAULT_LANGUAGE` to the language the database text is written in, and set `STM_CONF` `language.default` to the same value, before upgrading. The upgrade stops before it changes anything when the variable is missing, when `STM_CONF` has no `language.default`, when the two differ, or when that language is not in `STM_LANGUAGE`. The variable does not replace `STM_CONF`. The Spring Boot process reads it. A Liquibase 4.29 command-line run passes the same value on that command, as `-D=upgrade.defaultLanguage=<language>`. A deployment that relies only on the `sitmun.language` property still has to set `STM_CONF`, because the upgrade SQL cannot read the property. A new install does not read the variable.

With the published images, put `SITMUN_UPGRADE_DEFAULT_LANGUAGE` in `.env` and start the `1.3.0` backend image with `docker compose up -d --pull always --no-build`. Compose forwards the variable to the backend. An empty value leaves a new install unchanged.

A database that already has every 1.2.8 changelog row is upgraded in place when its 1.2.9-only rows, if any, are a prefix of the 1.2.9 master order. A full 1.2.9 database is that prefix. A database that stopped partway through 1.2.9 is accepted only when the rows it does have are the leading ones. A gap, such as changeset 21 without changeset 20, stops with `upgrade to 1.2.8 first`. A database with none of the 1.2.8 rows and no `stm_app` table is a new install and loads the baseline. A database that has `stm_app` but is older than 1.2.8 stops with `upgrade to 1.2.8 first` and is left unchanged. Two cartography rows that share `geo_styid` stop with `shared geo_styid` and are left unchanged. An extra changelog row added after 1.2.9 is allowed.

A finished 1.2.9 database on PostgreSQL, or on Oracle 23, skips the catch-up. Those changelog rows are already present, and the hop below runs. Oracle before 23 cannot finish the released 1.2.9 changelog. Changeset 22c uses `SELECT` without `FROM` and the literal `TRUE`, which are Oracle 23ai syntax. An install on Oracle 11 or Oracle 21 stops at that changeset. Oracle 19c was not tested; Oracle 21 is the stand-in. That partial database, and any 1.2.8 database, follows [Upgrade 1.2.8 to 1.3.0](1.2.8-to-1.3.0.md).

The check is the first changelog that runs: [00-version-check.postgresql.sql](../../sitmun-backend/src/main/resources/db/changelog/upgrade/00-version-check.postgresql.sql) and [00-version-check.oracle.sql](../../sitmun-backend/src/main/resources/db/changelog/upgrade/00-version-check.oracle.sql). The hop steps are under `db/changelog/upgrade/1.2.9-to-1.3.0/`. The required rows are the fixtures under `sitmun-backend/src/test/resources/db/databasechangelog/1.2.9/`.

## What an upgrade changes

The schema change is the catalog difference between the tagged 1.2.9 database and a fresh 1.3.0 database. On PostgreSQL 16, [02-schema.postgresql.sql](../../sitmun-backend/src/main/resources/db/changelog/upgrade/1.2.9-to-1.3.0/02-schema.postgresql.sql) makes the catalogs match: 369 columns, 143 constraints, and 72 indexes. On Oracle 23, [02-schema.oracle.sql](../../sitmun-backend/src/main/resources/db/changelog/upgrade/1.2.9-to-1.3.0/02-schema.oracle.sql) makes columns and indexes match, and makes each key cover the same columns with the same delete rule. Primary keys that 1.2.9 created without a name keep the name Oracle assigned. The difference is:

- `pgi_options` on `stm_par_gi`
- tables `stm_par_gs`, `stm_service_check`, `stm_service_check_sample`, and `stm_service_usage`. The two observed times are stored with a time zone
- `tas_title` on `stm_task`, 250 characters, optional
- configuration `setup.languageConfigured` set to `true`, because the upgraded database is already configured
- `tno_active` becomes mandatory, default on
- `use_email` becomes 250 characters
- unique index `stm_ltr_literal_uk` on the literal text
- [06-tree-node-type.sql](../../sitmun-backend/src/main/resources/db/changelog/upgrade/1.2.9-to-1.3.0/06-tree-node-type.sql) fills an empty tree type with `cartography` when the tree has a layer and no task. On a cartography or edition tree, an empty node type becomes `cartography` when the node has a layer, and `folder` when it has neither a layer nor a task. A type that is already set stays.

Existing tables are not created again. The baseline changesets are marked already run when the 1.2.9 schema changeset is present. See the preconditions in [db.changelog-master.yaml](../../sitmun-backend/src/main/resources/db/changelog/db.changelog-master.yaml).

System code-list rows are matched by list and value, never by id. A missing row is inserted with the next free id, `COD_SYSTEM` true, and the shipped description in the confirmed default language. A row that is already there is set to `COD_SYSTEM` true. Its description is not changed. Rows that were already system in 1.2.9 also get the shipped default flag. Rows that become system in 1.3.0 keep a partner's default. A value a partner deleted comes back. `downloadTask.scope` values `A`, `U`, and `C` stay removable.

The lists whose values become fixed are `applicationParameter.type`, `cartography.geometryType`, `cartography.legendType`, `cartographyFilter.type`, `cartographyFilter.valueType`, `cartographyParameter.format`, `cartographyParameter.geometryKind`, `cartographyParameter.preferredGeometryType`, `cartographyParameter.type`, `cartographyServiceParameter.type`, `cartographySpatialSelectionParameter.format`, `cartographySpatialSelectionParameter.type`, `databaseConnection.driver`, `serviceParameter.type`, `territory.scope`, `user.identificationType`, and `userPosition.type`. The four JDBC drivers are `org.h2.Driver`, `org.postgresql.Driver`, `oracle.jdbc.OracleDriver`, and `com.microsoft.sqlserver.jdbc.SQLServerDriver`. The shipped rows are every `cod_system` true line in [codelists.csv](../../tools/seed-data/baseline/codelists.csv). The values the product code reads are [required-codelists.yaml](../../sitmun-backend/src/test/resources/required-codelists.yaml).

Portuguese (`pt-PT`) is added when `lan_shortname = 'pt-PT'` is absent. The new row takes the next free `LAN_ID`, name `Português`, order 6, and enabled. An existing Portuguese row keeps its id, name, order, and enabled flag. Missing `Language.name` rows for Portuguese and for the other shipped languages in Portuguese are inserted the same way as other translations: matched by shortname, never by id. Code-value, task, and template-sentence labels for Portuguese are not part of this hop; those labels fall back to the default language.

Translations are inserted only for a language that is already in the database, only when that element, column, and language are absent, and not for the database's default language. The element id is the id in this database. `TRA_ID` uses the fresh-install id when it is free, otherwise the next free id. Existing translation rows are not renumbered. An English code-value label is corrected only when it still holds the wrong text shipped earlier. Translations of tasks, territory types, and task groups are not added when their base names are not in English, because the upgrade finds those rows by the English name.

A template sentence value is inserted when the sentence is already in the database, the language is already in the database, and that language has no value for the sentence. A value that is already there is not changed. A sentence a partner deleted is not inserted again. Each new value takes the next free `LTV_ID`, one statement per row. The title of More Info Advanced is not part of this hop.

Each `STM_SEQUENCE` counter becomes whichever is higher: its current value, or one past the highest id in that table. A counter does not move backward. A fresh install sets each counter to one past the highest id in that table.

## What stays

A fresh 1.3.0 database has the same columns, foreign keys, constraint names, and system code lists on H2, Oracle, and PostgreSQL. PostgreSQL spells a boolean as `boolean` and Oracle as `number(1)`. A string is `character varying` on PostgreSQL and H2, and `varchar2` on Oracle. The literal-translation-value primary key is `stm_ltv_pkey` on all three. A PostgreSQL database that already used the longer name is renamed. Oracle primary keys created without a name keep the `SYS_C` name. Service-check times that were stored before the column gained a time zone are copied as UTC. Application rows, including code-list rows an administrator created, keep their ids. The profile changelog files [profiles/postgres/liquibase/master.xml](../../profiles/postgres/liquibase/master.xml) and [profiles/oracle/liquibase/master.xml](../../profiles/oracle/liquibase/master.xml) include the shipped master. The profile configuration points at `classpath:/db/changelog/db.changelog-master.yaml`.
