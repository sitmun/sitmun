# Upgrade 1.2.9 to 1.3.0

`sitmun.client.unsafe-allowed-hosts` is empty unless the deployment sets it. An empty list checks the certificate and the hostname of every upstream server. A deployment that reaches a self-signed server sets `SITMUN_CLIENT_UNSAFE_ALLOWED_HOSTS` to those hosts, or to `*`. `*` turns the checks off for every host. With Docker Compose, put it in `.env`. The 1.3.1 `compose.yaml` forwards it to the backend and the proxy. The 1.3.0 `compose.yaml` does not, so on 1.3.0 add `- SITMUN_CLIENT_UNSAFE_ALLOWED_HOSTS=${SITMUN_CLIENT_UNSAFE_ALLOWED_HOSTS:-}` under `environment:` of both services ([#378](https://github.com/sitmun/sitmun/issues/378)).

Set `SITMUN_UPGRADE_DEFAULT_LANGUAGE` to the language the database text is written in, and set `STM_CONF` `language.default` to the same value, before upgrading. The upgrade stops before it changes anything when the variable is missing, when `STM_CONF` has no `language.default`, when the two differ, or when that language is not in `STM_LANGUAGE`. The variable does not replace `STM_CONF`. The Spring Boot process reads it. A Liquibase 4.29 command-line run passes the same value on that command, as `-D=upgrade.defaultLanguage=<language>`. A deployment that relies only on the `sitmun.language` property still has to set `STM_CONF`, because the upgrade SQL cannot read the property. A new install does not read the variable.

With the published images, put `SITMUN_UPGRADE_DEFAULT_LANGUAGE` in `.env` and start the `1.3.0` backend image with `docker compose up -d --pull always --no-build`. Compose forwards the variable to the backend. An empty value leaves a new install unchanged.

A database that already has every 1.2.8 changelog row is upgraded in place when its 1.2.9-only rows, if any, are a prefix of the 1.2.9 master order. A full 1.2.9 database is that prefix. A database that stopped partway through 1.2.9 is accepted only when the rows it does have are the leading ones. A gap, such as changeset 21 without changeset 20, stops with `upgrade to 1.2.8 first`. A database with none of the 1.2.8 rows and no `stm_app` table is a new install and loads the baseline. A database that has `stm_app` but is older than 1.2.8 stops with `upgrade to 1.2.8 first` and is left unchanged. Two cartography rows that share `geo_styid` stop with `shared geo_styid` and are left unchanged. An extra changelog row added after 1.2.9 is allowed.

A finished 1.2.9 database on PostgreSQL, or on Oracle 23, skips the catch-up. Those changelog rows are already present, and the hop below runs. Oracle before 23 cannot finish the released 1.2.9 changelog. Changeset 22c uses `SELECT` without `FROM` and the literal `TRUE`, which are Oracle 23ai syntax. That changeset file is not in this tree. The syntax is recorded in the root changelog history, and the 1.2.9 fixtures under `sitmun-backend/src/test/resources/db/databasechangelog/1.2.9/` include the row. An install on Oracle 11 or Oracle 21 stops at that changeset. Oracle 19c was not tested; Oracle 21 is the stand-in. That partial database, and any 1.2.8 database, follows [Upgrade 1.2.8 to 1.3.0](1.2.8-to-1.3.0.md).

The `FILENAME` of a 1.2.x row depends on the Liquibase that wrote it. The 4.29 and 4.30 command lines record each included file. Liquibase 4.31.0 and later, which every 1.2.x backend ran (4.33.0 in 1.2.0 and 1.2.1, 4.31.1 from 1.2.2), record `master.xml`, the profile changelog's `logicalFilePath`, for every changeset. The check matches rows by id, author, and file name. Before it, [00-restore-changelog-filenames.postgresql.sql](../../sitmun-backend/src/main/resources/db/changelog/releases/1.3.1/00-restore-changelog-filenames.postgresql.sql) and [00-restore-changelog-filenames.oracle.sql](../../sitmun-backend/src/main/resources/db/changelog/releases/1.3.1/00-restore-changelog-filenames.oracle.sql) match each `sitmun` row by id, whatever its file name, and set it to the file that id belongs to in the 1.2.9 master. Then they run the same check in the same block. A refusal rolls the renames back. A row that already names its file, a row from another author, and a row whose id is not in that master are left alone. On Oracle, the same step accepts the stack `dev` fix for changeset 22c (sitmun/sitmun-application-stack#74), which ran 22, 22b, and 22c again as 26, 26b, and 26c. Each 26 changeset writes what its 22 counterpart writes. When a 22 row is missing and its 26 row is present, the step records the 22 row as `MARK_RAN` with `applied as <26 id>` in `COMMENTS`, and keeps the 26 row. A database that already ran the 1.3.0 check skips this step.

The check then runs: [00-version-check.postgresql.sql](../../sitmun-backend/src/main/resources/db/changelog/upgrade/00-version-check.postgresql.sql) and [00-version-check.oracle.sql](../../sitmun-backend/src/main/resources/db/changelog/upgrade/00-version-check.oracle.sql). The hop steps are under `db/changelog/upgrade/1.2.9-to-1.3.0/`. The required rows are the fixtures under `sitmun-backend/src/test/resources/db/databasechangelog/1.2.9/`.

## What an upgrade changes

The schema change is the catalog difference between the tagged 1.2.9 database and a fresh 1.3.0 database. On PostgreSQL 16, [02-schema.postgresql.sql](../../sitmun-backend/src/main/resources/db/changelog/upgrade/1.2.9-to-1.3.0/02-schema.postgresql.sql) applies the changes below. On Oracle 23, [02-schema.oracle.sql](../../sitmun-backend/src/main/resources/db/changelog/upgrade/1.2.9-to-1.3.0/02-schema.oracle.sql) makes columns and indexes match, and makes each key cover the same columns with the same delete rule. Primary keys that 1.2.9 created without a name keep the name Oracle assigned. The difference is:

- `pgi_options` on `stm_par_gi`
- tables `stm_par_gs`, `stm_service_check`, `stm_service_check_sample`, and `stm_service_usage`. The new observed-time columns are stored with a time zone. They are created empty. A database that already had those times without a time zone is copied as UTC by [service-check-observed-timestamptz.postgresql.sql](../../sitmun-backend/src/main/resources/db/changelog/service-check-observed-timestamptz.postgresql.sql) and [service-check-observed-timestamptz.oracle.sql](../../sitmun-backend/src/main/resources/db/changelog/service-check-observed-timestamptz.oracle.sql), which are master changesets, not this hop
- `tas_title` on `stm_task`, 250 characters, optional
- `tno_active` becomes mandatory, default on
- `use_email` becomes 250 characters
- `code_otp`, `tre_image_name`, `tno_style`, and `tno_view_mode` widen to 255 characters
- unique index `stm_ltr_literal_uk` on the literal text
- unique key `stm_geo_uk_styid` on `geo_styid`
- [06-tree-node-type.sql](../../sitmun-backend/src/main/resources/db/changelog/upgrade/1.2.9-to-1.3.0/06-tree-node-type.sql) fills an empty tree type with `cartography` when the tree has a layer and no task. On a cartography or edition tree, an empty node type becomes `cartography` when the node has a layer, and `folder` when it has neither a layer nor a task. A type that is already set stays
- [07-legend-type.sql](../../sitmun-backend/src/main/resources/db/changelog/upgrade/1.2.9-to-1.3.0/07-legend-type.sql) renames legend type `CAPABILITIES` to `LEGENDURL` and updates the shipped legend descriptions

First-run uses the built-in admin password. `setup.languageConfigured` is not stored. Those are product rules, not columns added by `02-schema`.

Existing tables are not created again. The baseline changesets are marked already run when the 1.2.9 schema changeset is present. See the preconditions in [db.changelog-master.yaml](../../sitmun-backend/src/main/resources/db/changelog/db.changelog-master.yaml).

System code-list rows are matched by list and value, never by id. A missing row is inserted with the next free id, `COD_SYSTEM` true, and the shipped description in the confirmed default language. A row that is already there is set to `COD_SYSTEM` true. Its description is not changed. Rows that were already system in 1.2.9 also get the shipped default flag. Rows that become system in 1.3.0 keep a partner's default. A value a partner deleted comes back. `downloadTask.scope` values `A`, `U`, and `C` stay removable.

The lists whose values become fixed are `applicationParameter.type`, `cartography.geometryType`, `cartography.legendType`, `cartographyFilter.type`, `cartographyFilter.valueType`, `cartographyParameter.format`, `cartographyParameter.geometryKind`, `cartographyParameter.preferredGeometryType`, `cartographyParameter.type`, `cartographyServiceParameter.type`, `cartographySpatialSelectionParameter.format`, `cartographySpatialSelectionParameter.type`, `databaseConnection.driver`, `serviceParameter.type`, `territory.scope`, `user.identificationType`, and `userPosition.type`. The four JDBC drivers are `org.h2.Driver`, `org.postgresql.Driver`, `oracle.jdbc.OracleDriver`, and `com.microsoft.sqlserver.jdbc.SQLServerDriver`. The shipped rows are every `cod_system` true line in [codelists.csv](../../tools/seed-data/baseline/codelists.csv). The values the product code reads are [required-codelists.yaml](../../sitmun-backend/src/test/resources/required-codelists.yaml).

Portuguese (`pt-PT`) is added when `lan_shortname = 'pt-PT'` is absent. The new row takes the next free `LAN_ID`, name `Português`, order 6, and enabled. An existing Portuguese row keeps its id, name, order, and enabled flag. Missing `Language.name` rows for Portuguese and for the other shipped languages in Portuguese are inserted the same way as other translations: matched by shortname, never by id. [04-translations](../../sitmun-backend/src/main/resources/db/changelog/upgrade/1.2.9-to-1.3.0/04-translations.postgresql.sql) also inserts Portuguese code-value and task labels. [04b-literal-values](../../sitmun-backend/src/main/resources/db/changelog/upgrade/1.2.9-to-1.3.0/04b-literal-values.postgresql.sql) inserts Portuguese template-sentence values. Oracle uses the matching `.oracle.sql` files.

Translations are inserted only for a language that is already in the database, only when that element, column, and language are absent, and not for the database's default language. The element id is the id in this database. `TRA_ID` uses the fresh-install id when it is free, otherwise the next free id. Existing translation rows are not renumbered. An English code-value label is corrected only when it still holds the wrong text shipped earlier. Translations of tasks, territory types, and task groups are not added when their base names are not in English, because the upgrade finds those rows by the English name.

A template sentence value is inserted when the sentence is already in the database, the language is already in the database, and that language has no value for the sentence. A value that is already there is not changed. A sentence a partner deleted is not inserted again. Each new value takes the next free `LTV_ID`, one statement per row. The title of More Info Advanced is not part of this hop.

Each `STM_SEQUENCE` counter becomes whichever is higher: its current value, or one past the highest id in that table. A counter does not move backward. A fresh install sets each counter to one past the highest id in that table.

## What stays

A fresh 1.3.0 database has the same columns, foreign keys, constraint names, and system code lists on H2, Oracle, and PostgreSQL. PostgreSQL spells a boolean as `boolean` and Oracle as `number(1)`. A string is `character varying` on PostgreSQL and H2, and `varchar2` on Oracle. The literal-translation-value primary key is `stm_ltv_pkey` on all three. A PostgreSQL database that already used the longer name is renamed. Oracle primary keys created without a name keep the `SYS_C` name. Application rows, including code-list rows an administrator created, keep their ids. The profile changelog files [profiles/postgres/liquibase/master.xml](../../profiles/postgres/liquibase/master.xml) and [profiles/oracle/liquibase/master.xml](../../profiles/oracle/liquibase/master.xml) include the shipped master. The profile configuration points at `classpath:/db/changelog/db.changelog-master.yaml`.
