# Upgrade 1.2.9 to 1.3.0

A database that already has every 1.2.9 changelog row is upgraded in place. A database with none of those rows is a new install and loads the baseline. A database that has some of them and is missing one stops with `upgrade to 1.2.9 first` and is left unchanged. An extra changelog row added after 1.2.9 is allowed.

Oracle 11 and Oracle 21 cannot run changeset 22c. Their 1.2.9 database uses [26_map_image_task_type_pre23.yaml](../../tools/tests/26_map_image_task_type_pre23.yaml) in that slot. The version check accepts that history.

The check is the first changelog that runs: [01-version-check.postgresql.sql](../../sitmun-backend/src/main/resources/db/changelog/legacy/01-version-check.postgresql.sql) and [01-version-check.oracle.sql](../../sitmun-backend/src/main/resources/db/changelog/legacy/01-version-check.oracle.sql). The required rows are the fixtures under `sitmun-backend/src/test/resources/db/databasechangelog/1.2.9/`.

## What an upgrade changes

The schema change is the catalog difference between the tagged 1.2.9 database and a fresh 1.3.0 database. On PostgreSQL 16, [02-schema.postgresql.sql](../../sitmun-backend/src/main/resources/db/changelog/legacy/02-schema.postgresql.sql) makes the catalogs match: 369 columns, 143 constraints, and 72 indexes. On Oracle 23, [02-schema.oracle.sql](../../sitmun-backend/src/main/resources/db/changelog/legacy/02-schema.oracle.sql) makes columns and indexes match, and makes each key cover the same columns with the same delete rule. Primary keys that 1.2.9 created without a name keep the name Oracle assigned. The difference is:

- `pgi_options` on `stm_par_gi`
- tables `stm_par_gs`, `stm_service_check`, `stm_service_check_sample`, and `stm_service_usage`
- `tno_active` becomes mandatory, default on
- unique index `stm_ltr_literal_uk` on the literal text

Existing tables are not created again. The baseline changesets are marked already run when the 1.2.9 schema changeset is present. See the preconditions in [db.changelog-master.yaml](../../sitmun-backend/src/main/resources/db/changelog/db.changelog-master.yaml).

System code-list rows are matched by list and value, never by id. A missing row is inserted with the next free id and `COD_SYSTEM` true. A row that is already there is set back to the shipped description, default flag, and system flag. That includes a value a partner deleted. The shipped rows are every `cod_system` true line in [codelists.csv](../../tools/seed-data/baseline/codelists.csv). The values the product code reads are [required-codelists.yaml](../../sitmun-backend/src/test/resources/required-codelists.yaml).

Translations are inserted only for a language that is already in the database, and only when that element, column, and language are absent. The element id is the id in this database. `TRA_ID` uses the fresh-install id when it is free, otherwise the next free id. Existing translation rows are not renumbered.

Each `STM_SEQUENCE` counter becomes whichever is higher: its current value, or one past the highest id in that table. A counter does not move backward. A fresh install sets each counter to one past the highest id in that table.

## What stays

Application rows, including code-list rows an administrator created, keep their ids. The profile changelog files [profiles/postgres/liquibase/master.xml](../../profiles/postgres/liquibase/master.xml) and [profiles/oracle/liquibase/master.xml](../../profiles/oracle/liquibase/master.xml) include the shipped master. The profile configuration points at `classpath:/db/changelog/db.changelog-master.yaml`.
